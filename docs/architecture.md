# System Architecture

This document describes the end-to-end architecture of the Retail BDA Analytics Platform, clearly distinguishing between the intended production Big Data infrastructure and the currently active local fallback environment.

## 1. Complete Architecture Diagram

```text
Retail CSV Dataset
        ↓
Data Validation
        ↓
HDFS Storage Layer
        ↓
MapReduce Processing
        ↓
Hive / Local Analytics
        ↓
FastAPI REST API
        ↓
React + Vite Dashboard
        ↓
Charts / KPIs / Tables
```

## 2. Infrastructure Tiers

### Tier 1: Data Generation & Ingestion
- **Component:** Synthetic Data Generator
- **Output:** `data/retail_logs.csv`
- **Role:** Simulates high-volume retail transactions across multiple channels, categories, and cities.

### Tier 2: Storage Layer
- **Intended Component:** Hadoop Distributed File System (HDFS)
- **Current Component:** Local OS File System
- **Role:** Holds the raw CSV data and stores intermediary and final outputs from MapReduce and Hive.

### Tier 3: Batch Processing Layer
- **Intended Component:** Hadoop MapReduce (Java/Python via Streaming)
- **Current Component:** Local MapReduce Simulator (Python)
- **Role:** Performs heavy aggregation tasks (Total Revenue, Category sums) utilizing `mapper.py` and `reducer.py` scripts.

### Tier 4: Data Warehousing & Analytics Layer
- **Intended Component:** Apache Hive
- **Current Component:** Python Local Analytical Fallback
- **Role:** Applies schema-on-read to the raw data and executes complex aggregations (Daily Trends, Top Products) using SQL-like operations.

### Tier 5: Serving Layer (API)
- **Component:** FastAPI (Python)
- **Role:** Exposes processed analytics safely to web consumers. It checks the outputs generated by Tier 4, parses TSV files, and returns strongly-typed JSON.

### Tier 6: Presentation Layer (UI)
- **Component:** React, Vite, Recharts (JavaScript)
- **Role:** Fetches JSON from the Serving Layer and renders Interactive dashboards with KPI cards, bar charts, and pie charts.

## 3. The Role of the "Local Fallback"

Because setting up a full Hadoop and Hive cluster on a standard Windows academic environment is often unfeasible, this project employs a **Local Fallback** architecture. 

- **How it works:** Whenever the platform detects the absence of `hdfs` or `hive` executables, it falls back to native Python scripts that process the data identically.
- **Why it matters:** This ensures the end-to-end pipeline (CSV -> API -> Dashboard) remains demonstrably unbroken, while retaining all the HQL and MapReduce artifacts required to run on a real cluster when available.
